CBR Model: a research engine for Tom's Candle Behavior Reversal method

Turn a discretionary, video-taught gold-trading method into a deterministic, evidence-traced system. Then find out, with out-of-sample data, whether it has a real edge and which conditions create it.

Primary objective

The one question this project answers

Does the CBR method contain a repeatable, robust edge on XAUUSD, and which conditions define that edge?

Success is a trustworthy answer, including "no edge". It is not the highest historical win rate. A setup-finding TradingView indicator is the end product only if validation supports it.

Context & problem

Tom teaches CBR across four course libraries (15-minute CBR, hourly CBR, Phase 1 foundations, Phase 2) and a public trading journal. The method is internally consistent but taught visually and discretionarily. Words like "decisive", "high volume" and "clean" carry real weight but have no numbers. His reported results (e.g. "80% win rate with DXY") come from hand-journaled trades with no sample sizes, and a manual backtest of about 10 trades in a month he chose himself.

Trading a method like this without testing invites three failure modes: hindsight bias (judging setups by their outcome), overfitting (tuning rules until history looks good), and unfaithful translation (coding something that isn't what was taught). This project is designed to prevent all three.

Goals & non-goals

Goals

  • A complete, traceable written and machine specification of the 15m and 1h CBR models
  • A Python reference engine that reproduces the taught setups with no lookahead
  • Baseline backtests of canonical rules only, before any optimisation
  • Chronological validation: development, validation and a holdout touched once
  • Ablation tests showing which confluences (DXY, AOI, sessions, 15m alignment) add information
  • A non-repainting TradingView indicator and alerts, after validation
  • A signal ledger that records every qualifying signal, taken or not

Non-goals

  • Maximising historical win rate or profit factor
  • Inventing rules the sources don't teach
  • Trading instruments other than XAUUSD, with DXY as context (USDJPY, silver and gold spread are out)
  • Automated live execution or broker integration
  • Publishing course material, transcripts or market data (repo is public)
  • Optimising parameters before baselines are established

Principles

Evidence hierarchy

Level 1: definesCourse videos

15m CBR, hourly CBR, Phase 1, Phase 2. The only source that defines rules.

Level 2: clarifiesJournal & live calls

TomTradesJournal videos and three recorded community calls. They illustrate rules and suggest experiments, but never redefine them.

Level 3: discoveredBacktest findings

Always labelled RESEARCH-DERIVED, never "original CBR rule".

Non-negotiables

  • Every rule cites evidence: video, timestamp and a verbatim quote, verified by automated tests.
  • Every number is labelled: CANON (cites evidence), ASSUMPTION (cites an open question and pre-declares its test range) or IMPL (engineering only). Enforced by a config contract test.
  • No lookahead, no repainting. UTC everywhere; decisions use only closed bars.
  • Setup validity is judged at entry, never from the outcome.
  • Chronological splits only. Hypotheses are logged before tests; the holdout is used once per frozen version.
  • Missing data lowers confidence. It is never filled with a neutral default.
  • Local-first. Keys stay in gitignored files; copyrighted material and market data are never committed.

The models

Both CBR models trade the same idea at two scales: a candle opens and pushes hard one way for roughly its first half, then price reverses toward the middle of that push. Timing comes from candle behavior; entries come from a market-structure shift.

Non-functional

  • Reproducibility: pinned tools, file hashes, frozen model versions (rules + params + code hash + data hash).
  • Traceability: rule → evidence → timestamp, and param → evidence or open question.
  • Privacy & licensing: no market data, course material or keys in git; nothing leaves the machine except public data fetches.
  • Cost control: paid data only after an explicit quote and approval; download scripts refuse more than 5% over the quote.

Validation & success criteria

Performance is judged on expectancy in R and its stability, not win rate. The gates below are proposed and need owner sign-off before Phase 15.

Gate 1: faithful implementation (Phase 13)

The engine reproduces the taught course setups. Every mismatch is classified as code bug, data difference, declared simplification or source ambiguity.

Gate 2: baseline has something (Phases 15-16)

Positive expectancy after costs on the development split with a sample large enough to judge (minimum trade count to be fixed in the hypothesis log beforehand), and the same sign on the validation split.

Gate 3: robust edge (Phases 20-22)

Walk-forward out-of-sample expectancy stays positive, the bootstrap confidence interval for expectancy excludes zero, no single year carries the result, and drawdown and losing-streak distributions are survivable. The holdout confirms once.

Gate 4: indicator worth building (Phase 26)

Only rules and confluences that passed ablation on out-of-sample data go into the production indicator. A quality score ships only if higher scores outperform lower scores out-of-sample.

A "no edge" result at any gate is a valid outcome and ends or redirects the project. It does not trigger rule-tweaking until something looks profitable.
